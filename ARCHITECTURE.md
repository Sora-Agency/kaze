# Kaze · Architecture

Kaze is a native macOS app by Sora Agency. The bundle identifier is
`com.soraagency.kaze`. Build with `scripts/build.sh`; verify behavior with
`scripts/test.sh` and visual layouts with `scripts/preview.sh`.

## Source boundaries

- **App/**: entry point, navigation shell, identity and preference migration.
- **Domain/**: storage, files, deletion assessments, scheduling entities and
  validation. No SwiftUI views, filesystem traversal, path resolution or launchd mutations.
- **Infrastructure/**: metadata scanning, process execution, application and
  resource discovery, path resolution and classification, journaled analysis
  removal, transactional schedule persistence and launchd adapters.
- **Features/**: each feature owns its views and observable presentation state.
  Explorer and scheduled tasks have dedicated models. Application and resource
  actions extend the shared CleanerModel to coordinate selections and cleanup.
- **DesignSystem/**: Sora colors/type, Lucide vectors, reusable buttons, hover
  states and motion. Views use these components instead of individual styles.
- **Localization/**: English/Spanish catalogs, locale selection and interpolation.
  `L10n` resolves display text without changing persisted values or user data.
  `localization.zsh` shares the same language policy for scheduled cleanup.
- **Icons/Lucide/**: original pinned SVG assets and their ISC license.
- **cleaner.zsh / cleanup-lock.zsh**: cleaning engine and cross-process exclusion.
  Multiple scheduled tasks wait their turn, with a bounded wait.

Views submit intent to observable models; filesystem and process work belongs
in Infrastructure. Background work returns UI mutations to the main actor.
AnalysisRemoval owns the fresh-file/process checks and journaled Trash move;
SmartScanModel retains selection, cancellation and presentation state. Tests
inject the move and process inventory into the same removal path used by the app.
Shared analysis headers, status notices and finding rows live in Features/Analysis
and serve Smart Scan, Duplicates, System Data and Development. Assistant download
and context views are separate components; the screen owns conversation input.
ScheduleService accepts an injected LaunchCommandRunning adapter and home
folder; tests never touch real user agents or execute cleanup. The scanner
reads metadata without following symlinks or downloading file contents.

## Packaging and migration

Build and preview discover Swift sources recursively. Generated distribution
files live in `build/staging.noindex`; `package` is a convenience symlink.
The binary package contains only the app, installer, uninstaller, documentation
and licenses. Launchd agents are generated by ScheduleService when tasks are
activated; no fixed launchd template is shipped. Builds prepare a fresh package
and replace the previous output only after compilation and signing succeed.
The DMG uses a compact Sora layout with a TIFF background containing standard
and Retina representations. Finder icon view metadata selects the background
and icon sizes explicitly. Background aliases omit the temporary writable image
reference so they resolve inside the final compressed volume. Distribution tests
resolve the alias without mounting another image and check both representations.
Source ZIPs are rebuilt from a clean directory. Icon PNGs and ICNS are generated
from Brand/SoraLogo.svg in a temporary build directory. Test and preview binaries
are temporary; only preview images remain in build/previews.
Binary ZIPs include the host architecture in their filename and ship with a
SHA-256 manifest. Source ZIPs include README, contribution guidance, public
screenshots and the GitHub workflow.
The installer verifies the incoming app and replaces the complete bundle after
backing up the installed version, so removed resources cannot survive an update.

Version tag pushes run the same macOS build matrix, then a separate Linux job
assembles and uploads a draft release. Only that job has repository write
permission. `scripts/prepare-release.py` checks version metadata, both artifact
manifests and source equivalence before generating the shared assets and hashes.
`scripts/create-draft-release.sh` creates or completes a draft while preserving
edited notes; it refuses to modify a published release. Release tests use a fake
GitHub CLI and temporary files, without contacting GitHub.

Schedule schema 3 keeps UUIDs and settings from schema 2, changes job labels to
`com.soraagency.kaze.task.<uuid>` and removes old labels in one transaction.
Failed migrations restore old agents and retain old JSON. A backup precedes
each migration. Explicitly enabled schedules stay enabled; defaults remain off.
Old bundle IDs appear only in compatibility code so old installs can migrate
and be uninstalled. New code must use AppIdentity for product identification.

Lucide geometry is compiled into SwiftUI Path code, rendered as vectors with
consistent 2/24 strokes. `scripts/vendor-lucide.py` updates the pinned subset;
icons need no network at build time or runtime. Motion is scoped to interactions,
section transitions, presentation and progress; Reduce Motion removes motion
and scene inactivity pauses animated loading indicators.

Input chrome is shared by text, search, numeric, time and selection controls.
Text uses native SwiftUI editing; time uses a borderless NSDatePicker to retain
macOS validation and keyboard navigation. Custom toggle styles render Lucide
checks and Sora switches while exposing native checkbox/switch semantics through
accessibilityRepresentation. Disabled and focused states use the same palette
and respect Reduce Motion. Form, focus and disabled previews are generated in
both themes by `scripts/preview.sh`.

## Public screenshots

`scripts/screenshots.sh` renders the real SwiftUI views using
`tests/PreviewFixtures.swift`: a virtual /Users/demo home, seeded file metadata
and fixed disk capacity. Initial explorer entries skip filesystem traversal;
CleanerModel receives a storage snapshot with log reads and discovery disabled.
Scheduling reads a temporary fixture store through a simulated launchd runner.
Public images contain no real user folders, application inventory or logs.

## Languages

The bundle declares English and Spanish. The in-app selector persists
`kaze.language`; macOS preferences provide the initial language, with English
as fallback. L10n synchronizes its language state for background work and caches
both resource bundles. AppLanguageStore publishes changes to open views and menus
without replacing their identity or restarting scans. SwiftUI and native time
controls update their locale together. Presentation messages retain their keys
and arguments so existing status and safety text can resolve in either language.
Runtime cleanup uses an explicit language for manual runs and the saved preference
for scheduled runs, falling back to macOS preferences when no choice exists.
Count messages use native plural catalogs. Stored enum values and user-entered
names are language independent. LegalView resolves translated terms and privacy
resources; MIT and third-party licenses retain their original wording.

## Updates

AppUpdater owns one main-actor SPUStandardUpdaterController for every window.
Kaze checks on startup when enabled and Sparkle schedules subsequent checks.
KVO keeps the sidebar and menu state synchronized; user changes use Sparkle's
persisted preference API. Preview builds exclude the updater and never check
for updates. The first build fetches a checksum-pinned Sparkle 2.10.0 distribution,
embeds its complete framework and helpers with preserved symlinks and signatures,
and links with a bundle-relative rpath. Each build selects its architecture's
GitHub Releases latest-download feed in the bundled Info.plist.
The dependency cache keeps the framework, signing tools and license; Sparkle's
demo app and debug symbols are discarded after archive verification.

Both the feed and DMG are EdDSA signed and verified before extraction. System
profiling and unattended installation are disabled. Tag builds use a repository
secret to generate feeds with embedded release notes and verify their signatures
on macOS. Release assembly validates metadata, architecture and hashes before
including both feeds in the draft. The private signing key stays out of source
and release assets; the public key is committed in Info.plist.

DiskAccessStore refreshes on launch and when the app becomes active. Its shield
indicator reflects whether the app can open a protected file, without reading
or changing its contents. Because macOS has no public Full Disk Access status
API, this is a capability probe, not an authoritative TCC setting query. Missing
files and UNIX permission errors remain unverified; a successful probe enables
the green shield-check. Previews inject fixed states and do not probe host files.

## Storage intelligence

Analysis models, allocation accounting, signed policies, fingerprints and
operation records live in Domain. Infrastructure owns StorageIndexer,
DuplicateDetector (streaming SHA-256 and thumbnail Vision), RuleCatalog,
ApplicationAttribution, OperationJournal and mutation leases. SmartScanModel
owns a serial utility queue and cancellation generations, publishing one shared
index for Map, Duplicates, System Data, Developer Mode and Local Assistant.
AnalysisCache persists bounded, versioned binary plists of metadata in the private
`~/Library/Caches/Kaze/Analysis-v1` directory: 96 MiB per Smart Scan, 8 MiB per
folder, 128 MiB total and 32 folder snapshots. Derived index dictionaries are
rebuilt on loading. Writes are atomic on utility queues; invalid, missing or
oversized cache data falls back to scanning. File contents and deletion authority
are never persisted. Restored Smart Scan results retain their measurement date,
clear all selections and remain stale until an explicit fresh scan. Hashes are
not recomputed at launch. Mutation notifications invalidate the saved index.

Explorer shows saved rows immediately and checks historical macOS FSEvents before
reusing recursive measurements. One scoped event stream runs only while Explorer
is visible, coalesces changes and refreshes affected first-level subtrees on its
existing serial utility queue. Monitoring starts before a new walk; events during
that walk trigger a follow-up pass, retaining a conservative event checkpoint.
Root inode, device UUID and event IDs are checked. Dropped/reset history, mount
changes, incomplete results, external volumes, temporary/system variable folders,
or snapshots older than 24 hours force a full background walk. FSEvents are
advisory; explicit Refresh always performs a complete measurement. Cross-child
hard links also force full walks whenever content changes, preserving one parent
inode set. Explorer retains dated rows during refresh/cancellation, bounds memory
snapshots to 32 folders/50,000 entries and ignores its own cache-write events.
See [Apple's FSEvents guidance](https://developer.apple.com/library/archive/documentation/Darwin/Conceptual/FSEvents_ProgGuide/UsingtheFSEventsFramework/UsingtheFSEventsFramework.html).
No full analysis or app/resource inventory runs automatically at window creation.

Metadata is fully streamed; retained details are limited separately. Totals
use inode deduplication and st_blocks; sparse logical sizes never become capacity
recovery estimates. APFS sharing prevents a guaranteed recovery figure. Payload
reads only occur for duplicate comparison and explicitly selected Quick Look.
Cloud/provider, backup and Photos protections are path- and metadata-based.
Signed scopes and closed processes are checked before cache mutation, including
fresh subtree metadata to reject protected descendants. Exact duplicate copies
and their preserved original are freshly hashed before Trash operations.

New operations have per-UUID atomic JSON records in the local Operations folder.
The journal shares cleanup-lock exclusion with scheduled tasks. Restoring re-reads
persisted records, validates Trash metadata and atomically refuses overwrites.
Native resource deletion and irreversible scheduled cache cleanup are recorded
without claiming free-space deltas as file-attributable capacity recovery.

OperationCLI handles short-lived policy/journal calls from the existing zsh
engine before GUI startup. There is no second daemon. StorageMonitor runs a
filesystem capacity query once per minute in the GUI process, stops its timer
when disabled and emits notifications only after explicit opt-in. The assistant
keeps verified recommendations independent of its optional local LLM.
LocalAIPackage pins engine/model versions, sizes and SHA-256. LocalAIService
uses ephemeral URLSession downloads, private staging and atomic activation;
checks and downloads occur only in the assistant's serial utility queue.
LocalAssistantModel never downloads on initialization or availability checks.
Queries extract the verified engine into a private temporary directory, run
llama-completion with 2 CPU threads, no GPU, 4096 context and 384 output tokens,
and stop on cancellation or a 90-second deadline. No server or daemon is started.
LocalAssistantPrompt includes bounded measured categories and verified rule
summaries, without file contents or full paths. AI has no tools or deletion API.
Optional AI requires macOS 13.3; existing features remain macOS 13-compatible.
See [the AI guide](docs/LOCAL_AI.md) for versions and privacy.

Smart Scan keeps its summary outside the lazy result list and uses a permanent
native scroll observer to publish only compact/expanded threshold crossings. Category
cards appear at the top and hide while scrolling; the three summary cards stay fixed.
Result rows
remain lazy and paged. The assistant keeps the latest question and answer paired,
with a fixed composer and a separate scrollable context column. Verified findings
are grouped by rule only when the findings publisher changes, preserving measured
recovery ranges and avoiding repeated grouping during input edits.

The rule manifest is bundled and Ed25519-signed; builds and runtime verify it.
Changes must be signed with scripts/sign-rules.sh and tested before shipping.
Public previews seed metadata and a temporary journal; they never run host
inventory or real cleanup commands. See [the guide](docs/STORAGE_ANALYSIS.md)
for scopes, thresholds, retained-detail limits and recovery constraints.

Smart Scan's compact header animates only its summary container with a 380 ms
collapse curve; Reduce Motion disables it. A scoped local scroll/key observer
requires upward input to expand the header, preventing viewport clamping on short
lists from triggering a collapse/expand loop. Both native observation tokens are
removed on teardown. Settings and safety exposes monitor choices and protection
status first; signatures and each rule's audit details remain in disclosure groups.
Assistant accents use the shared brand palette; success/warning colors retain
their semantic meaning.

## Recovery and startup apps

RecoveryModel and StartupItemsModel own their serial utility queues and keep
work off the main actor. Their initialization does not inventory disks, read
login items or request authorization. The navigation shell retains both models
while switching sections. Recovery entries, devices, volumes and outcomes live
in Domain; parser internals and recovery-specific errors stay in Infrastructure/Recovery.
Recovery's APFS reader is split into container,
B-tree, index, compression and extraction adapters; the independent copy operation
owns destination creation and reports. RecoverySource authorizes device descriptors
through a small C adapter using posix_spawn/authopen with O_RDONLY and cancellation.
Disk topology checks require an external APFS source and a separate physical
output disk. Raw images are regular files opened with O_RDONLY/O_NOFOLLOW.
Parser caches and record counts are bounded; cancellation propagates through
forgiving traversal rather than being swallowed as corruption.

StartupItemsService injects LoginItemsManaging. Its System Events adapter passes
JSON arguments to a fixed JXA script, with bounded output and a timeout. Mutations
save disabled references atomically, use a per-user mutation lease, and verify
macOS state afterward. StartupItemsError belongs to Domain. ToolCommandRunner
and the thread-safe OperationCancellation are shared infrastructure and do not
depend on APFS types. Startup tests compile without the recovery parser or C
authorization adapter, enforcing that boundary. Modern background services stay
in Apple's native settings.
Tests never mutate actual user login items. See docs/RECOVERY_AND_STARTUP.md for
scope, persistence and recovery limits.
